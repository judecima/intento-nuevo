## Question

Can historical complexity families identify the V10 p95/p99 tail early enough to route only the expensive minority through a specialized path?

## Data

The test pairs 2,000 historical orders with:

- V10 runtime/result.
- Two cheap/baseline runs over the same order.
- Fast features available before a deeper search:
  - piece count,
  - Fast board count,
  - Fast elapsed time.

The family key is deliberately simple:

`piece-count bucket × Fast board-count bucket`

Fast elapsed time is used only as a tie-break at the learned family boundary.

No V10 output is used as an online feature.

## Anti-leakage protocol

Orders are sorted by historical order number.

The model is trained only on earlier orders and tested on later orders.

Four expanding windows are used:

- train 0..599 -> test 600..999
- train 0..999 -> test 1000..1399
- train 0..1399 -> test 1400..1799
- train 0..1599 -> test 1600..1999

The learned rule is a real per-order threshold: the future test set is not ranked in advance.

## Result

### Target approximately 10% expensive routing

Actual mean routed share: **12.4%**

- mean p95-tail recall: **93.8%**
- minimum p95-tail recall in any window: **75%**
- mean p99-tail recall: **100%**
- minimum p99-tail recall in any window: **100%**
- mean share of V10 CPU concentrated in routed orders: **71.6%**

### Target approximately 20% expensive routing

Actual mean routed share: **21.6%**

- mean p95-tail recall: **100%**
- minimum p95-tail recall in any window: **100%**
- mean p99-tail recall: **100%**
- minimum p99-tail recall in any window: **100%**
- mean share of V10 CPU concentrated in routed orders: **87.2%**

Thus the 20% policy captured the complete p95 and p99 tail in all four chronological validation windows.

## Interpretation

The useful signal is not an exact-project cache. It is an advisory complexity router.

This experiment does **not** show that p95/p99 already fell. It shows that the engine can identify, from cheap information already available after Fast, a small subset containing essentially all of the expensive tail.

The next gate must run the current Performance V1 candidate on that routed subset and compare end-to-end latency while preserving:

- board count,
- physical placement/digest where equivalence is required,
- remnant quality,
- industrial validation,
- deterministic fallback.

## Safety constraints

Family memory must only:

- prioritize,
- allocate effort,
- warm-start,
- choose which safe acceleration to try first.

It must never:

- return a structural-family plan directly,
- remove the fallback solely because of family membership,
- skip rounds 21..40 without a certificate,
- relax validation.

Historical evidence already contains a counterexample (`4058501`) where late rounds are required for a real board-count improvement.
